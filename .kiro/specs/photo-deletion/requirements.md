# Requirements Document

## Introduction

This document specifies requirements for adding photo deletion functionality to the PICME photo retrieval system. Currently, administrators can upload photos to events but cannot remove unwanted or incorrect photos after upload. This feature enables admins to delete individual photos from events, ensuring that only relevant photos remain in the system and contribute to face recognition searches.

## Glossary

- **System**: The PICME photo retrieval application
- **Admin**: An authenticated user with administrative privileges (is_admin = True)
- **Photo**: An image file uploaded to an event, stored in the filesystem with metadata in the database
- **Event**: A collection of photos with associated metadata (name, date, location)
- **Face_Embedding**: A numerical vector representation of a detected face, generated by FaceNet or ArcFace models
- **Filesystem**: The server's file storage where photo files are physically stored
- **Database**: The SQLite database storing photo metadata, embeddings, and relationships
- **Photo_Record**: The database entry in the photos table containing metadata about a photo
- **Cascade_Deletion**: Automatic deletion of related child records when a parent record is deleted

## Requirements

### Requirement 1: Photo Deletion Authorization

**User Story:** As an admin, I want only authorized administrators to delete photos, so that event photo collections are protected from unauthorized modification.

#### Acceptance Criteria

1. WHEN a non-admin user attempts to access the photo deletion endpoint, THE System SHALL return an authorization error and prevent deletion
2. WHEN an admin user is not authenticated, THE System SHALL redirect to the login page
3. WHEN an authenticated admin accesses the photo deletion endpoint, THE System SHALL allow the deletion to proceed

### Requirement 2: Delete Individual Photos

**User Story:** As an admin, I want to delete individual photos from an event, so that I can remove unwanted or incorrect photos from the collection.

#### Acceptance Criteria

1. WHEN an admin requests deletion of a photo by photo ID, THE System SHALL remove the photo file from the filesystem
2. WHEN an admin requests deletion of a photo by photo ID, THE System SHALL remove the Photo_Record from the database
3. WHEN a Photo_Record is deleted, THE System SHALL automatically delete all associated Face_Embedding records through Cascade_Deletion
4. WHEN the photo file does not exist in the filesystem, THE System SHALL still remove the Photo_Record from the database and return success
5. IF the photo ID does not exist in the database, THEN THE System SHALL return a 404 error

### Requirement 3: Photo Deletion User Interface

**User Story:** As an admin, I want a delete button on each photo in the event view, so that I can easily remove unwanted photos.

#### Acceptance Criteria

1. WHEN viewing an event's photos, THE System SHALL display a delete button on each photo card
2. WHEN an admin clicks the delete button, THE System SHALL display a confirmation dialog before deletion
3. WHEN an admin confirms deletion, THE System SHALL send a DELETE request to the photo deletion endpoint
4. WHEN deletion succeeds, THE System SHALL remove the photo from the UI without requiring a full page reload
5. WHEN deletion fails, THE System SHALL display an error message to the admin

### Requirement 4: Photo Deletion Feedback

**User Story:** As an admin, I want clear feedback when deleting photos, so that I know whether the deletion succeeded or failed.

#### Acceptance Criteria

1. WHEN a photo deletion succeeds, THE System SHALL display a success message to the admin
2. WHEN a photo deletion fails due to a file system error, THE System SHALL display an error message with details
3. WHEN a photo deletion fails due to a database error, THE System SHALL display an error message with details
4. WHEN the network request fails, THE System SHALL display a connection error message

### Requirement 5: Maintain Event Statistics After Deletion

**User Story:** As an admin, I want event statistics to update after photo deletion, so that the displayed photo and face counts remain accurate.

#### Acceptance Criteria

1. WHEN a photo is deleted, THE System SHALL update the total photo count for the event
2. WHEN a processed photo is deleted, THE System SHALL update the processed photo count for the event
3. WHEN the last photo in an event is deleted, THE System SHALL display the "No photos uploaded yet" empty state

### Requirement 6: Safe File System Operations

**User Story:** As a system administrator, I want photo deletion to handle file system errors gracefully, so that database integrity is maintained even when file operations fail.

#### Acceptance Criteria

1. IF the photo file cannot be deleted from the filesystem due to permissions, THEN THE System SHALL log the error and still remove the Photo_Record
2. IF the photo file path is invalid, THEN THE System SHALL log the error and still remove the Photo_Record
3. WHEN a photo deletion encounters a database error, THE System SHALL rollback the transaction and preserve the Photo_Record
4. THE System SHALL log all photo deletion attempts with timestamp, photo ID, and outcome

### Requirement 7: Delete Button Visual Design

**User Story:** As an admin, I want the delete button to be visually distinct but not intrusive, so that I can easily manage photos without accidental deletions.

#### Acceptance Criteria

1. THE System SHALL display the delete button with a red color scheme to indicate a destructive action
2. THE System SHALL display a trash icon on the delete button for visual clarity
3. WHEN hovering over the delete button, THE System SHALL display a darker shade to indicate interactivity
4. THE System SHALL position the delete button consistently on all photo cards

### Requirement 8: Confirmation Dialog Content

**User Story:** As an admin, I want the confirmation dialog to clearly describe what will be deleted, so that I can avoid accidentally deleting the wrong photo.

#### Acceptance Criteria

1. WHEN the confirmation dialog appears, THE System SHALL display the photo filename being deleted
2. WHEN the confirmation dialog appears, THE System SHALL warn that the action cannot be undone
3. WHEN the confirmation dialog appears, THE System SHALL provide "Cancel" and "Delete" action buttons
4. WHEN the admin clicks "Cancel", THE System SHALL close the dialog without deleting the photo

### Requirement 9: Concurrent Photo Deletion Safety

**User Story:** As a system administrator, I want the system to handle concurrent deletion requests safely, so that database integrity is maintained when multiple admins work simultaneously.

#### Acceptance Criteria

1. WHEN two admins attempt to delete the same photo simultaneously, THE System SHALL allow the first request to succeed
2. WHEN two admins attempt to delete the same photo simultaneously, THE System SHALL return a 404 error for the second request
3. THE System SHALL use database transactions to ensure atomic deletion operations
4. WHEN a deletion transaction fails, THE System SHALL rollback all changes

### Requirement 10: HTTP API for Photo Deletion

**User Story:** As a developer, I want a RESTful API endpoint for photo deletion, so that the feature follows web standards and can be tested independently.

#### Acceptance Criteria

1. THE System SHALL provide a DELETE endpoint at /admin/photos/<photo_id>/delete
2. WHEN the deletion succeeds, THE System SHALL return HTTP status 200 with a JSON success message
3. WHEN the photo is not found, THE System SHALL return HTTP status 404 with a JSON error message
4. WHEN authorization fails, THE System SHALL return HTTP status 403 with a JSON error message
5. WHEN a server error occurs, THE System SHALL return HTTP status 500 with a JSON error message
